# Ranged input audit — Custard Knights

Read-only audit of `work/custard-knights-plan` at `main937cb80` (latest stated tested build `beta7runtime6f1300b`). No gameplay or execution tests run. The original `../custard-knights` bakery WIP was not inspected or changed. Source wiring is not ergonomic acceptance.

## Findings by mode

- **Arena:** Mouse movement aims the first local player; held left-click attacks and right-click guards. `fire()` uses character facing for bows, cannon, bombs and other weapon shots. Cursor position remains active while inside the canvas, so aim persists while stationary; pointer leave/cancel resets it. A cursor crosshair is drawn. See [`index.html`](https://github.com/joshharris-sparkedfm/custard-knights/blob/937cb80/index.html) 990–996 (shot direction), 1014–1027 (mouse), 1054–1068 (ownership), 1243–1245 (facing), 2462 (reticle).
- **Arena controller:** Standard right stick reads axes 2/3; aim is supplied above magnitude `.5`, after per-axis `.22` deadzone. Left stick/d-pad moves; A/RT attack, B/LB dash, X/RB/LT guard. When stick aim is neutral, movement sets facing; when neither aims nor moves, facing persists. Right stick can aim independently while moving. Heavy melee uses hold-and-release attack, not a separate heavy button. See `index.html` 1037–1043, 1049–1068, 1243–1245, 1267–1269.
- **Story and Cup:** Reuse arena `humanInput`/`update`, so mouse, pad, reticle and thresholds apply. Story boots a one-human FFA engine (`index.html` 3128–3136); Cup rounds use normal arena modes/maps (`game/cup.js` 3, 20; `index.html` 3113, 3122). Story’s ranged lesson is chiefly defending against archer shots; source does not show a player ranged weapon in every encounter. Story is solo; Cup inherits arena mouse-to-player-1 routing.
- **Faction Front:** Separate layer. Mouse aims at a world point relative to the local player; left click attacks, right-click guards. Keyboard J/L(or Shift)/K attack/heavy/guard. Pad right stick aims, A attacks, RT heavy, LT guard, B dash, X ability. Component deadzone `.18`; aim updates above magnitude `.1`. Aim persists at stick center; keyboard movement supplies aim, then retains it when stopped. Simulation angles the player from aim independently of movement and snapshots facing when attack starts. See [`game/mass-battle-ui.js`](https://github.com/joshharris-sparkedfm/custard-knights/blob/937cb80/game/mass-battle-ui.js) 50, 114–126; [`game/mass-battle.js`](https://github.com/joshharris-sparkedfm/custard-knights/blob/937cb80/game/mass-battle.js) 213–214, 328–330, 348–349. No explicit reticle was found in Faction drawing (UI 150–158); feedback is facing/weapon pose. It reads only the first connected standard pad (114) and has no touch controls (50).

## Gaps and acceptance

Arena mouse state is global. Standard mapping gives it only to player 1; couch-seat mapping attaches it only to `kb1` (`index.html` 1054–1056). The reticle checks whether any `kb1` seat exists, while input requires that seat own the current entity. Mixed-device ownership, especially a mouse user assigned elsewhere, needs explicit acceptance. Faction Front appears single-local-player; no couch-seat routing is evidenced.

Source cannot establish precision, camera-follow feel, responsive deadzones, or play-scale feedback. Human shots follow facing; no human target snapping is present. Faction lacks an explicit reticle, and arena has no controller reticle.

Accept by physically verifying a ranged weapon in arena, Story and Cup: mouse aims/click fires at cursor while moving independently; reticle tracks the intended world point and aim remains stable when stationary. Verify mixed-seat ownership. On pad, right stick aims independently of left-stick movement, neutral retains aim without jitter, and heavy/guard remain usable. Repeat Faction mouse/pad checks, with visible aim feedback and its separate heavy/guard bindings. Record physical-device results; source review alone cannot pass ergonomic acceptance.
